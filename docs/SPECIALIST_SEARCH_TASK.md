# Задание 3. Публичный ID, поиск и «Мои специалисты»

## Цель

Заменить использование внутреннего `Business.id` во внешнем интерфейсе отдельным
публичным ID специалиста и завершить пользовательский сценарий поиска.

После выполнения пользователь должен иметь возможность:

1. увидеть публичный ID в профиле специалиста;
2. ввести этот ID в разделе «Мои специалисты»;
3. увидеть найденный профиль до добавления;
4. открыть услуги выбранного бизнеса;
5. добавить бизнес в «Мои специалисты» или удалить его оттуда;
6. вернуться к сохранённому профилю без повторного ввода ID;
7. открыть профиль по Telegram-ссылке, содержащей публичный ID.

Существующий поиск формально работает, но принимает внутренний `Business.id` и показывает
только название. Это задание заменяет временное поведение полноценным публичным сценарием.

## Что означает ID специалиста

В интерфейсе используется понятное название «ID специалиста». В модели это публичный код
конкретного Business, а не `User.id`, `telegram_id` или primary key таблицы.

Один пользователь может владеть двумя бизнесами с разными услугами и расписаниями.
Поэтому каждый Business получает свой публичный ID. Поиск по нему открывает ровно один
профиль и не объединяет два бизнеса автоматически.

Пример ожидаемого смысла:

```text
Один владелец
├── Бизнес «Логопед Анна»      → публичный ID A7K29Q
└── Бизнес «Онлайн-консультации» → публичный ID M4R8TX
```

Формат является частью внешнего интерфейса. После выпуска его нельзя менять без плана
совместимости ссылок и сохранённых кодов.

## Инструменты и библиотеки

Дополнительный пакет для генерации ID не требуется:

- `secrets` стандартной библиотеки — криптографически стойкий случайный выбор;
- `string` — разрешённый алфавит;
- Pydantic — проверка формата модели;
- Aiogram Router, FSM и callback — Telegram-сценарий;
- существующие Repository и Transaction — атомарная проверка и сохранение;
- pytest и pytest-asyncio — тесты.

Не использовать `random` для публичных ID. Не использовать Telegram ID, последовательный
номер строки, короткую часть имени или номер телефона. Внешний код не должен позволять
угадывать следующий профиль.

## Требования к публичному ID

Публичный ID должен быть:

- отдельным полем Business;
- случайным, а не последовательным;
- уникальным среди всех бизнесов;
- стабильным после создания;
- нечувствительным к регистру при поиске;
- сохранённым в одном нормализованном регистре;
- достаточно коротким для ручного ввода;
- состоящим из заранее утверждённого набора латинских букв и цифр;
- без пробелов и символов, которые Telegram или URL могут трактовать отдельно;
- отличным от внутреннего ID и Telegram ID.

Рекомендуется исключить визуально похожие символы, если это улучшает ручной ввод.
До реализации зафиксировать длину, алфавит и пример в pull request. Не уменьшать пространство
вариантов до уровня, при котором профили легко перебирать.

Unique constraint будущего SQL Server остаётся последней защитой от совпадения. Логика
должна уметь повторить генерацию при коллизии, не перезаписывая чужой профиль.

## Изменение модели и старых JSON-данных

В Business появляется публичный код. Он должен сериализоваться тем же способом, что и
другие поля Pydantic-модели.

Существующий `data/notebook.json` может содержать бизнесы без нового поля. Требуется
явная миграция версии JSON-схемы:

- старому Business назначается один стабильный публичный ID;
- два бизнеса получают разные ID;
- миграция не меняет услуги, расписания, клиентов и записи;
- повторный запуск не генерирует новый ID;
- повреждённый файл не перезаписывается;
- при неудаче исходный файл сохраняется;
- версия схемы обновляется только после полного успешного преобразования.

Нельзя полагаться на Pydantic default, который будет генерировать новое значение при
каждом чтении старого объекта до сохранения файла.

## Методы сервисного слоя

Telegram-обработчик не вызывает `tx.list()` и не ищет Business самостоятельно. В Catalog
нужно выделить операции со следующими обязанностями:

- нормализовать введённый публичный ID;
- найти Business по точному публичному ID;
- вернуть безопасную ошибку, если профиль не найден;
- создать уникальный ID внутри транзакции создания Business;
- получить публичные данные профиля;
- определить, сохранён ли выбранный Business у текущего пользователя;
- добавить или удалить Favorite идемпотентно;
- получить список сохранённых Business без смешивания их услуг и расписаний.

Названия методов согласовать с текущим стилем Catalog. Не менять назначение существующего
`business(id)`: внутренние callback приложения по-прежнему могут использовать primary key.
Поиск публичного профиля должен быть отдельной операцией, чтобы внутренний и внешний ID
нельзя было случайно перепутать.

## Экран владельца

В управлении каждым бизнесом показать:

- подпись «ID специалиста»;
- публичный ID;
- ссылку на профиль, построенную из публичного ID;
- подсказку, что ID можно отправить клиенту;
- действие для просмотра профиля глазами клиента.

Внутренний `Business.id` больше не показывать как код. Telegram ID владельца также не
показывать. Если у владельца два бизнеса, на каждом экране отображается собственный ID.

Изменение публичного ID пользователем в MVP не требуется. Это позволяет сохранить уже
распространённые ссылки. Возможность смены кода требует отдельной политики старых ссылок.

## Поиск из «Мои специалисты»

Сценарий:

1. пользователь открывает «Мои специалисты»;
2. выбирает поиск по ID;
3. бот объясняет, где взять ID, и принимает строку;
4. ввод нормализуется;
5. сервис выполняет точный поиск;
6. бот показывает карточку результата;
7. пользователь решает открыть профиль или сохранить бизнес;
8. после сохранения профиль появляется в «Мои специалисты».

Карточка результата должна содержать достаточно данных для различения двух бизнесов:

- название бизнеса;
- имя специалиста;
- краткое описание;
- формат или адрес в объёме публичного профиля;
- принимает ли бизнес новые записи;
- публичный ID;
- активные услуги либо действие их просмотра;
- текущее состояние сохранения.

Поиск не является общим каталогом по именам, городу или профессии. Частичное совпадение,
выдача похожих ID и список всех профилей не входят в MVP.

## «Мои специалисты»

Список строится через существующую сущность Favorite, связанную с Business.

Требуется:

- показать сохранённые бизнесы;
- открыть правильный профиль по каждой кнопке;
- явно подписать действие «Добавить» или «Удалить» в зависимости от состояния;
- не создавать дубликаты при повторном callback;
- корректно показать пустой список;
- сохранить поиск как доступное действие при непустом списке;
- предусмотреть разбиение на страницы, если список перестаёт помещаться в сообщение;
- не показывать скрытые услуги клиента;
- показать профиль, даже если новые записи временно выключены;
- запретить новую запись в выключенном профиле существующим правилом.

Если пользователь сохраняет два бизнеса одного владельца, они остаются двумя отдельными
позициями, потому что имеют разные услуги, расписания и публичные ID.

## Deep link

Новая ссылка профиля содержит публичный ID, а не primary key. При открытии бот заново
ищет Business и показывает клиентский профиль.

Нужно определить переходный период для уже созданных тестовых ссылок с внутренним ID:

- временно поддержать их без повторной публикации внутреннего ID; либо
- показать понятное сообщение и новую ссылку владельцу.

Выбранный вариант описать в pull request и покрыть тестом. Новые ссылки всегда создаются
только с публичным ID.

## Проверка доступа и защита от перебора

Публичный ID предназначен для открытия публичного профиля, но не предоставляет права
владельца. Любое изменение Business, Service, расписания или Appointment по-прежнему
проверяет `owner_id` в сервисном слое.

Ошибочный формат и отсутствующий код должны давать одинаково безопасный ответ без
внутреннего ID, SQL и трассировки. Поиск не сообщает, какие соседние коды существуют.

Оценить необходимость простого ограничения частоты повторных попыток для одного
Telegram-пользователя. Если оно не входит в этот этап, зафиксировать риск и обеспечить
достаточно большое пространство случайных кодов.

## Обработка ошибок

Проверить следующие случаи:

- пустой ввод;
- пробелы до и после ID;
- нижний и смешанный регистр;
- недопустимые символы;
- слишком короткая и слишком длинная строка;
- несуществующий ID;
- коллизия при генерации;
- повторное нажатие добавления или удаления;
- удалённый Business, оставшийся в Favorite;
- выключенный приём новых записей;
- старая deep link;
- одновременное создание двух Business;
- открытие двух бизнесов одного владельца.

Ожидаемые ошибки проходят через `RuleError`. Ошибка уникальности в SQL Server или JSON
не должна показываться пользователю как текст драйвера.

## Тесты

### Модель и генерация

- формат соответствует утверждённому алфавиту и длине;
- два бизнеса получают разные значения;
- ID не равен internal ID и Telegram ID;
- нормализация регистра и пробелов;
- симуляция коллизии приводит к повторной попытке, а не перезаписи;
- повторное чтение сохраняет тот же ID.

### Миграция JSON

- файл предыдущей версии получает стабильные коды;
- два старых Business получают разные коды;
- все старые связи сохраняются;
- повторная загрузка не меняет значения;
- ошибка не уничтожает исходный файл;
- неизвестная версия схемы останавливает запуск.

### Сервисный слой

- точный поиск существующего кода;
- одинаковый результат для нижнего и верхнего регистра;
- неизвестный код возвращает ожидаемую ошибку;
- внутренний ID нельзя использовать как публичный код;
- Favorite относится к найденному Business;
- два бизнеса одного владельца не смешиваются;
- публичный поиск не даёт права изменения.

### Telegram-сценарий

- ID виден владельцу и клиенту;
- поиск показывает карточку до добавления;
- добавление и удаление обновляют подпись действия;
- список переживает повторное открытие;
- deep link с публичным ID открывает профиль;
- недоступный профиль обрабатывается понятным сообщением;
- два публичных ID открывают два правильных бизнеса;
- callback старого экрана не меняет другой Favorite.

### SQL Server после объединения задания 2

- unique constraint действует без учёта регистра согласно выбранной нормализации;
- два параллельных создания не сохраняют одинаковый public_code;
- индекс используется для точного поиска;
- ORM-преобразование сохраняет поле без изменения.

## Порядок выполнения

1. Создать ветку `feature/public-specialist-id` от актуального `main`.
2. Зафиксировать формат и правила публичного ID в pull request.
3. Согласовать поле Business и порядок объединения с веткой SQL Server.
4. Добавить модель и миграцию существующего JSON.
5. Добавить операции Catalog и их тесты.
6. Перевести профиль и новую deep link на публичный ID.
7. Расширить поиск и карточку результата.
8. Завершить состояния «Моих специалистов».
9. Проверить два бизнеса одного владельца.
10. Запустить Ruff и весь pytest.
11. Проверить сценарий вручную двумя Telegram-аккаунтами.
12. Открыть pull request с результатами и описанием совместимости старых ссылок.

## Критерии готовности

- internal ID и Telegram ID не показываются как публичный код;
- каждый Business имеет отдельный стабильный публичный ID;
- поиск по ID открывает правильный профиль;
- два бизнеса одного владельца различаются;
- публичный ID используется в новой ссылке;
- поиск не обращается к JSON или SQL из Telegram-обработчика;
- Favorite добавляется и удаляется без дубликатов;
- старые JSON-данные мигрируются без потери связей;
- задача SQL Server получила совместимый unique field и индекс;
- ошибки не раскрывают внутренние данные;
- все старые и новые тесты проходят;
- pull request не содержит токенов, `.env`, базы, дампов и журналов.
