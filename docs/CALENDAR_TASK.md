# Задание 1. Универсальный календарь Telegram

## Цель

Добавить в Notebook единый календарь месяца для выбора дат. Один компонент должен
использоваться в нескольких сценариях, чтобы внешний вид и правила навигации не
расходились в разных частях бота.

Календарь требуется подключить к четырём сценариям:

1. мастер выбирает последний день, до которого клиенты могут записываться;
2. мастер открывает конкретную дату своего рабочего календаря;
3. клиент выбирает дату новой записи;
4. клиент выбирает новую дату при переносе существующей записи.

## Сначала изучить

- `src/notebook_bot/bot/common.py` — отправка сообщений, клавиатуры, общая обработка ошибок;
- `src/notebook_bot/bot/business.py` — настройки бизнеса и поле `horizon_days`;
- `src/notebook_bot/bot/schedule.py` — открытие конкретной даты и функция `render_day()`;
- `src/notebook_bot/bot/booking.py` — выбор даты клиентом и перенос записи;
- `src/notebook_bot/logic/catalog.py` — методы `dates()`, `times()` и `update_business()`;
- `src/notebook_bot/logic/availability.py` — правила, по которым дата становится доступной;
- `src/notebook_bot/models.py` — модели `Business`, `Service`, `Appointment`;
- `tests/test_telegram_flow.py` — пример проверки реального роутинга Aiogram без Telegram API;
- разделы расписания и переноса в продуктовом концепте.

Не обращаться из Telegram-обработчиков к JSON-файлу или будущей SQL-базе напрямую.
Календарь получает данные через объект `app` и существующие методы сервисного слоя.

## Инструменты и библиотеки

Использовать уже установленный Aiogram 3 и стандартную библиотеку Python:

- `calendar.Calendar(firstweekday=0)` — разбиение месяца на недели с понедельника;
- `datetime.date`, `datetime.timedelta` — границы и сравнение дат;
- `zoneinfo` через существующий `app.timezone` и `app.clock()` — текущая локальная дата;
- `aiogram.Router` и фильтры `F` — обработчики callback;
- `InlineKeyboardButton`, `InlineKeyboardMarkup` или готовые `kb()`/`one()` из `bot/common.py`;
- `CallbackData` из Aiogram допускается, если итоговая строка помещается в ограничение
  Telegram и остаётся понятной при отладке;
- `pytest` и `pytest-asyncio` — автоматические тесты.

Дополнительную библиотеку календаря подключать не требуется. Не добавлять
`aiogram-calendar`, `aiogram-dialog` и другие фреймворки только ради этого компонента:
они создадут второй способ навигации рядом с уже существующим роутингом проекта.

## Внешний вид календаря

Календарь должен показывать:

- название месяца и год;
- семь столбцов от понедельника до воскресенья;
- число каждого дня текущего месяца;
- переход к предыдущему и следующему месяцу, если переход разрешён;
- понятную кнопку отмены или возврата в исходный раздел;
- выбранную конечную дату;
- при необходимости — сегодняшнюю дату;
- недоступные даты без активного действия.

Сетка должна сохранять семь столбцов. Пустые позиции до первого и после последнего
числа месяца не должны выполнять бизнес-действия. Длинные названия и служебные символы
нужно проверить в мобильном Telegram, а не только по объектам клавиатуры в тесте.

Визуальные обозначения должны быть единообразными. До реализации зафиксировать в pull
request короткое описание обозначений: текущая дата, выбранная дата, доступная дата,
недоступная дата. Не полагаться только на цвет кнопки: Telegram не предоставляет
управление цветами inline-клавиатуры во всех клиентах.

## Режим 1. Последняя дата записи

В настройках бизнеса вместо ручного ввода количества дней открыть календарь месяца.
Мастер выбирает последнюю дату, доступную для новых записей. Дата включается в период:
если выбрано 25 октября, свободные слоты 25 октября ещё могут показываться клиенту.

Текущее хранилище использует `Business.horizon_days`. Выбранную дату требуется перевести
в число календарных дней от локальной сегодняшней даты и сохранить через:

```text
app.update_business(actor, business_id, "horizon_days", value)
```

Это указание определяет контракт интеграции, но не задаёт структуру обработчиков.
В Telegram нужно показывать конечную дату, а не только внутреннее число дней.

Правила:

- разрешена сегодняшняя дата: тогда дальше сегодня запись закрыта;
- прошлую дату выбрать нельзя;
- максимальная дата соответствует допустимому пределу сервиса;
- переход между месяцами не должен позволять обойти предел;
- настройка первого бизнеса не изменяет второй бизнес;
- повторный выбор той же даты безопасен;
- старая кнопка проверяется заново на сервере, а не принимается без проверки.

## Режим 2. Дата рабочего календаря мастера

Текущий экран `Календарь / конкретная дата` просит ввести дату текстом. Заменить этот
ввод календарём месяца. После выбора вызвать существующий сценарий отображения даты,
который показывает интервалы, закрытия, лимит, комментарии и записи.

Выбор даты должен сохранить `business_id`. При двух бизнесах одинаковая дата открывает
два разных календаря с независимыми услугами, расписанием и записями.

В этом режиме допускается просмотр прошлых дат, если он нужен для истории, но изменение
прошедшего расписания должно следовать существующим правилам сервисного слоя. Границы
просмотра прошлых дат и их визуальное состояние описать в pull request.

## Режим 3. Новая запись клиента

Доступные даты получать только через:

```text
app.dates(actor, service_id, start_day=...)
```

Календарь не должен самостоятельно повторять расчёт рабочего времени, дневного лимита,
закрытых интервалов, длительности услуги или перерыва. Если дата отсутствует в результате
`app.dates()`, она не является активной кнопкой.

Клиенту не сообщается, что дата исчезла из-за дневного лимита. Для пользователя это
просто дата без доступного времени. После выбора даты время получается существующим
методом `app.times()`.

При переключении месяца доступные даты запрашиваются заново. Нельзя сохранять список
навсегда в памяти обработчика: расписание и записи могли измениться после показа экрана.

## Режим 4. Перенос записи

При переносе календарь получает доступные даты с `appointment_id`. Это позволяет
сервисному слою учитывать длительность существующей записи и исключать саму переносимую
запись из проверки пересечений.

Календарь должен сохранять `appointment_id` до выбора времени. После выбора нового
времени применяется существующий сценарий переноса. Отдельное повторное подтверждение
после ясно обозначенного выбора времени не добавляется.

Если перенос инициировал мастер, новое время выбирает клиент. Календарь не должен давать
мастеру обойти это правило для карточки клиента, связанной с Telegram-пользователем.

## Callback-данные и состояние

Для каждого действия callback должен однозначно содержать:

- назначение календаря;
- отображаемый месяц или выбранную дату;
- идентификатор нужного объекта: бизнеса, услуги или записи;
- при необходимости идентификатор экрана возврата.

Telegram ограничивает размер `callback_data` 64 байтами. Не помещать в callback JSON,
полные описания, имя клиента или список доступных дат. Значения из callback считаются
непроверенным вводом: после нажатия заново проверить объект, права и границы даты.

FSM можно использовать для контекста многошагового сценария. При этом callback старого
сообщения не должен менять другой бизнес или другую запись. Возврат на главный экран
очищает незавершённое состояние по существующим правилам проекта.

## Обработка ошибок

Нужно обработать понятным сообщением и безопасным возвратом:

- неверный формат callback;
- неизвестный режим календаря;
- несуществующий месяц или дата;
- прошлую или слишком далёкую дату;
- бизнес, услугу или запись, которые удалены либо недоступны пользователю;
- изменение расписания между показом месяца и нажатием;
- отсутствие свободного времени после выбора даты;
- устаревшее состояние переноса;
- попытку открыть бизнес другого владельца.

Ожидаемые ошибки бизнес-правил должны проходить через существующий `RuleError`.
Непредвиденные ошибки не показываются пользователю с трассировкой и не скрываются пустым
`except`: их обрабатывает общий механизм приложения.

## Проверки

### Модульные тесты сетки

Проверить как минимум:

- месяц, который начинается в понедельник;
- месяц, который начинается в воскресенье;
- февраль обычного и високосного года;
- 28, 29, 30 и 31 день;
- правильное количество строк и семь столбцов;
- переход декабря в январь и января в декабрь;
- выделение текущей и выбранной даты;
- отсутствие активного callback у недоступных дат;
- длину каждого `callback_data` не более 64 байт.

### Интеграционные тесты Aiogram

Проверить без реального Telegram API:

- открытие календаря из настроек бизнеса;
- сохранение последней даты включительно;
- невозможность выбрать прошлую и слишком далёкую дату;
- независимые горизонты двух бизнесов;
- открытие конкретной даты выбранного бизнеса;
- показ клиенту только дат из `app.dates()`;
- повторный запрос доступности при переходе месяца;
- перенос с сохранением `appointment_id`;
- безопасную обработку старой кнопки;
- возврат в правильный экран.

## Порядок работы

1. Создать ветку `feature/month-calendar` от актуального `main`.
2. Описать режимы и формат callback в короткой заметке pull request.
3. Сначала реализовать и протестировать построение сетки без Telegram API.
4. Подключить выбор последней даты записи.
5. Подключить календарь конкретной даты мастера.
6. Подключить новую запись клиента.
7. Подключить перенос.
8. Проверить два бизнеса и старые сообщения.
9. Запустить `ruff check src tests` и `pytest -q`.
10. Провести ручную проверку в мобильном Telegram и приложить результат к pull request.

Не объединять ветку самостоятельно. В pull request перечислить изменённые сценарии,
результаты автоматических тестов, результат ручной проверки и известные ограничения.

## Критерии готовности

- существует один повторно используемый календарный компонент;
- календарь визуально читается на мобильном устройстве;
- четыре сценария используют его без дублирования расчёта доступности;
- последняя дата записи сохраняется и действует включительно;
- два бизнеса полностью разделены;
- клиент не видит внутреннюю причину недоступности даты;
- права и дата проверяются повторно после callback;
- старые кнопки не приводят к неправильному изменению;
- все новые и прежние тесты проходят;
- pull request не содержит `.env`, токенов, базы и локальных журналов.
