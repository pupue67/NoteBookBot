# Как связать три части

## Текущая цепочка

```text
Telegram-событие
  → bot/*.py
  → BookingService (logic/booking.py + Catalog)
  → Repository.transaction()
  → MemoryRepository с необязательным сохранением JSON
```

В `main.py` создаётся один объект приложения, middleware передаёт его обработчикам как `app`.
`actor` — внутренний ID пользователя, полученный сервером по Telegram from_user.id.
Нельзя доверять присланному в callback ID клиента или бизнеса без повторной проверки в логике.

Общие формы используют `bot/common.py`: имя формы, перечень полей и функция сохранения.
Тексты ошибок бизнес-правил возвращаются через `RuleError`. Непредвиденные ошибки
попадают в локальный журнал с фильтром токена.

## Подключение календаря

1. Новый модуль экспортирует `router` и функции построения календарной клавиатуры.
2. Роутер подключается в `main.py` в порядке, указанном в `docs/CALENDAR_TASK.md`.
3. `business.py`, `schedule.py` и `booking.py` передают календарю назначение и ID объекта.
4. Доступные даты и изменения получают через методы `app`, без чтения хранилища из бота.
5. Владелец проверяет pull request, тесты и внешний вид в мобильном Telegram.

## Подключение БД

1. Разработчик возвращает совместимый Repository из `database/db.py:create_repository()`.
2. Проверяет транзакции и модели на отдельной базе SQL Server Developer.
3. В `.env` задаётся `STORAGE=database` и `DATABASE_URL`.
4. `main.py:build_app()` подключает адаптер; логика и экраны используют те же методы.
5. JSON-данные не импортируются автоматически: миграция данных — отдельный согласованный шаг.

## Ветки

Каждый создаёт свою ветку от актуального main. Ветки можно назвать
`feature/month-calendar`, `feature/sql-server-adapter` и `feature/public-specialist-id`.
Не копировать готовые папки поверх чужой работы.
В pull request указать изменённый сценарий, проверку и необходимые новые настройки.
Руководитель объединяет готовые изменения после тестов и ручной проверки.

`models.py`, `repository.py`, `main.py`, зависимости и общие callback являются точками
интеграции. Изменения в них обсуждать до начала зависимой работы.

## Связь публичного ID и SQL Server

Задание 3 добавляет общий контракт `Business.public_code`. SQL Server-ветка должна
использовать то же имя, формат и правило уникальности. Если работа ведётся параллельно,
сначала согласуется контракт, затем SQL Server-ветка обновляется относительно коммита,
в котором поле появилось в `models.py`. Внутренний ID не заменяется публичным кодом:
оба значения имеют разное назначение.

## Что пока требует решения перед настоящим запуском

- Точный город / внутренний часовой пояс.
- Срок ожидания мастера и предоплаты; сейчас по 30 минут.
- Связывание ручной карточки клиента с Telegram-пользователем.
- Платная подписка сервиса, отзывы и публичная модерация.
- Сервер, резервные копии, распределённая очередь уведомлений и несколько процессов.
