# NoteBookBot

Telegram-бот онлайн-записи к частным специалистам на Python и Aiogram 3.31.0.
Один пользователь может пользоваться ботом как клиент и как мастер, а мастер может
создать до двух независимых бизнесов со своими услугами, расписанием, клиентами и
записями.

Текущий `main` содержит полный локальный MVP с JSON-хранилищем. Универсальный календарь
месяца, Microsoft SQL Server-адаптер и отдельный публичный ID специалиста оформлены как
следующие командные задачи и ещё не считаются завершёнными.

**Для участников команды:** [скачивание проекта, ветки, коммиты и Pull Request](docs/BRANCH_WORKFLOW.md).

## Быстрый запуск в Windows и Visual Studio Code

Откройте `Notebook.code-workspace` или корневую папку репозитория в VS Code.

```powershell
py -3.14 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
.venv\Scripts\python.exe -m pip install -e . --no-deps
Copy-Item .env.example .env
```

Если `.env` уже существует, не заменяйте его. Укажите в локальном файле новый токен:

```env
BOT_TOKEN=your_new_telegram_bot_token
STORAGE=json
DATA_FILE=data/notebook.json
CITY_TIMEZONE=Asia/Yekaterinburg
BOT_PROXY=system
```

Токен не должен попадать в GitHub, сообщения коммитов, Pull Request или скриншоты.
Один токен должен использовать только один polling-процесс.

Запуск из терминала:

```powershell
.venv\Scripts\python.exe -m notebook_bot.main
```

Либо выберите конфигурацию **Notebook: Telegram bot** и нажмите F5. Остановка в
терминале — `Ctrl+C`.

По умолчанию `BOT_PROXY=system` использует существующий системный прокси. Для прямого
подключения установите `BOT_PROXY=direct`. Прокси с логином и паролем хранится только в
локальном `.env`.

Проверки проекта:

```powershell
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\ruff.exe check src tests
```

## Что реализовано в текущем MVP

### Пользователь и бизнес

- Один Telegram-пользователь может быть клиентом и мастером одновременно.
- Мастер может создать до двух бизнесов.
- У каждого бизнеса отдельные услуги, настройки, клиенты, расписание и записи.
- Запись в первом бизнесе не блокирует такое же время во втором бизнесе владельца.
- Профиль можно открыть через клиентскую ссылку и сохранить в «Мои специалисты».
- Мастер может временно выключить приём новых записей без удаления профиля и записей.

### Услуги и длительность

- Создание, изменение и скрытие услуг.
- Фиксированная или персональная длительность услуги.
- Для нового клиента персональной услуги мастер вводит количество минут.
- Персональная длительность сохраняется для пары «клиент — услуга».
- Новую длительность можно применить к одной записи или к следующим записям.
- Если длительность не помещается перед следующей записью, предлагается перенос;
  продолжительность занятия не урезается.

### Расписание и доступность

- Недельный шаблон с несколькими рабочими интервалами в одном дне.
- Разрыв между интервалами используется как регулярный обед или перерыв.
- Для дня недели задаются лимит клиентов и регулярный комментарий.
- Конкретная дата может переопределить интервалы, лимит, комментарий и адрес.
- Для даты можно закрыть несколько произвольных промежутков или весь день.
- Изменение графика не удаляет существующие записи: конфликт показывается мастеру.
- Доступность учитывает длительность услуги, общий перерыв, минимальный срок до записи,
  горизонт записи, закрытые интервалы и лимит клиентов.
- Клиенту не показываются даты без свободного времени или с достигнутым лимитом.

### Записи

- Самостоятельная запись клиента и ручная запись мастером.
- Просмотр клиентских и мастерских списков записей.
- Перенос всегда выбирает новую дату и новое время.
- Когда перенос инициирует мастер, новое время выбирает клиент.
- После ясного выбора нового времени дополнительное подтверждение не требуется.
- Отмена, история действий, завершённый визит и неявка.
- Защита от повторных callback и изменения устаревшей карточки.
- Ручная предоплата: клиент сообщает о переводе, мастер отмечает проверку.
- Напоминания за сутки и за два часа без обязательного подтверждения визита.

### Хранение и надёжность локальной версии

- `STORAGE=json` сохраняет данные в `data/notebook.json`.
- `STORAGE=memory` хранит данные до остановки процесса.
- JSON записывается атомарно через временный файл.
- Неудачная операция не фиксирует частичные изменения.
- Локальная блокировка не позволяет запустить второй процесс с тем же JSON.
- Ожидаемые ошибки показываются пользователю без трассировки и внутренних данных.
- Токен удаляется из текста журналируемых непредвиденных ошибок.

## Как проверить вручную

1. Отправить боту `/start` и создать первый бизнес.
2. Добавить фиксированную услугу без предоплаты.
3. Настроить день: `10:00-13:00, 15:00-20:00`.
4. Открыть клиентскую ссылку со второго Telegram-аккаунта.
5. Выбрать услугу, дату и время и создать запись.
6. Предложить перенос от имени мастера; выбрать новую дату и время клиентом.
7. Создать персональную услугу, оформить новую запись и указать минуты мастером.
8. Закрыть часть дня поверх существующей записи и проверить предупреждение о конфликте.
9. Отменить запись и убедиться, что освободившееся время снова доступно.
10. Перезапустить процесс и убедиться, что данные восстановились из JSON.
11. Создать второй бизнес и проверить независимость услуг, календарей и записей.

## Архитектура и структура проекта

```text
Telegram-пользователь
        ↓
Telegram Bot API и Aiogram Dispatcher
        ↓
bot/*.py — сообщения, кнопки, callback и FSM
        ↓
logic/*.py — сценарии и бизнес-правила
        ↓
repository.py — независимый контракт хранения
        ↓
storage.py (JSON) или database/* (SQL Server)
```

```text
src/notebook_bot/
├── main.py              # Сборка зависимостей, роутеров и запуск polling
├── config.py            # Настройки из окружения
├── models.py            # Общие модели предметной области
├── repository.py        # Контракты Repository и Transaction
├── storage.py           # Рабочее memory/JSON-хранилище
├── bot/
│   ├── common.py        # Общие формы, клавиатуры, middleware и ошибки
│   ├── menu.py          # Главное меню
│   ├── business.py      # Профиль, настройки и поиск специалиста
│   ├── services.py      # Telegram-интерфейс услуг
│   ├── schedule.py      # Недельный график и конкретные даты
│   ├── booking.py       # Создание и ручная запись
│   ├── appointments.py  # Просмотр, перенос, отмена и статусы
│   └── notifications.py # Доставка уведомлений и напоминаний
├── logic/
│   ├── catalog.py       # Бизнесы, услуги, расписание, клиенты и избранное
│   ├── availability.py  # Эффективный график и свободные слоты
│   ├── booking.py       # Операции с записями
│   └── rules.py         # Проверка пользовательских значений
└── database/
    ├── db.py            # Будущая фабрика SQL Server Repository
    ├── models.py        # Будущие SQLAlchemy ORM-модели
    └── repository.py    # Будущий SQL Server-адаптер
```

`bot` не читает JSON или SQL напрямую. Обработчики получают объект `app` через
middleware и вызывают методы сервисного слоя. Благодаря этому способ хранения можно
заменить без переписывания Telegram-интерфейса.

## Командные задачи

Задачи описывают ожидаемый результат, границы файлов, интеграцию, обработку ошибок,
тесты и критерии готовности. Каждая выполняется в отдельной ветке и передаётся через
Pull Request.

### Задание 1 — универсальный календарь месяца

**Постановка:** [docs/CALENDAR_TASK.md](docs/CALENDAR_TASK.md)  
**Ветка:** `feature/month-calendar`  
**Основной новый файл:** `src/notebook_bot/bot/calendar.py`

Нужно создать один календарный компонент и применить его в четырёх сценариях:

1. выбор последней даты, до которой открыта запись;
2. открытие конкретной даты рабочего календаря мастера;
3. выбор даты новой записи клиентом;
4. выбор новой даты при переносе.

Календарь строит только Telegram-интерфейс. Доступные даты получает через `app.dates()`,
а правила лимита, длительности, перерывов и занятости остаются в `logic`.

Готовый результат должен поддерживать переходы между месяцами, семь столбцов недели,
неактивные недоступные даты, callback короче 64 байт, два независимых бизнеса,
устаревшие кнопки и возврат в исходный сценарий. Нужны модульные тесты сетки,
интеграционные тесты Aiogram и ручная проверка на мобильном Telegram.

### Задание 2 — Microsoft SQL Server-адаптер

**Постановка:** [docs/DATABASE_TASK.md](docs/DATABASE_TASK.md)  
**Ветка:** `feature/sql-server-adapter`  
**Рабочая область:** `src/notebook_bot/database/`, `alembic/`, `tests/database/`

Нужно реализовать тот же контракт Repository, который использует JSON-версия:

- SQLAlchemy 2 async и драйвер `aioodbc`;
- ORM-таблицы для всех сущностей;
- первичные и внешние ключи, `NOT NULL`, `UNIQUE` и `CHECK`;
- Alembic-миграции;
- атомарные транзакции с `commit` и `rollback`;
- защита от двойного бронирования при параллельных запросах;
- разделение данных двух бизнесов;
- преобразование ORM-моделей в общие Pydantic-модели;
- понятная ошибка конфигурации без показа строки подключения;
- интеграционные тесты на отдельной тестовой БД.

После готовности `STORAGE=database` должен переключать хранилище в `main.py`, не меняя
обработчики `bot` и правила `logic`. Импорт существующего JSON в SQL Server является
отдельной задачей и не должен выполняться автоматически.

### Задание 3 — публичный ID и законченный поиск специалиста

**Постановка:** [docs/SPECIALIST_SEARCH_TASK.md](docs/SPECIALIST_SEARCH_TASK.md)  
**Ветка:** `feature/public-specialist-id`  
**Точки интеграции:** `models.py`, `catalog.py`, `business.py`, `storage.py`, SQL Server

Нужно отделить случайный стабильный публичный код от внутреннего primary key и Telegram
ID. Публичный код используется в клиентской ссылке и точном поиске, но никогда не даёт
прав владельца.

Задача включает генерацию и нормализацию кода, обработку коллизий, миграцию старого JSON,
уникальный индекс SQL Server, карточку результата поиска, добавление и удаление Favorite,
deep link, два бизнеса одного владельца и одинаковый безопасный ответ для неверного или
несуществующего кода.

### Порядок объединения задач

1. Публичный ID сначала согласует поле `Business.public_code` с SQL Server-задачей.
2. SQL Server использует согласованное имя поля и правило уникальности.
3. Календарь не меняет модели и Repository без отдельного согласования.
4. После каждого объединения следующая ветка обновляется относительно актуального `main`.
5. Общая интеграция выполняется по [docs/INTEGRATION.md](docs/INTEGRATION.md).

Распределение файлов и границы ответственности находятся в
[OWNERSHIP.md](OWNERSHIP.md).

## Будущие модули и этапы после текущих задач

### 1. Постоянное хранилище состояний Telegram

Сейчас незавершённые FSM-формы находятся в памяти и теряются после перезапуска. Для
серверной версии потребуется Redis либо другое совместимое хранилище состояний:

- восстановление активного шага диалога;
- срок жизни незавершённых форм;
- очистка старых состояний;
- независимость нескольких процессов бота;
- запрет смешивания состояний двух пользователей и двух бизнесов.

### 2. Надёжная очередь уведомлений

Текущий worker подходит для одного локального процесса. Серверный модуль должен добавить:

- отдельную очередь отправки;
- блокировку одного уведомления одним worker;
- повторные попытки с увеличением интервала;
- идемпотентный ключ события;
- статус окончательной ошибки;
- наблюдаемость и журнал доставки;
- защиту от повторной отправки после аварийного перезапуска.

### 3. Развёртывание и эксплуатация

Перед публичным запуском нужны:

- контейнер или служба для непрерывной работы;
- отдельные окружения разработки и production;
- безопасное хранение токена и строки подключения;
- миграции при выпуске версии;
- резервные копии SQL Server и проверка восстановления;
- журналирование без персональных данных и секретов;
- health check, мониторинг ошибок и оповещение команды;
- политика обновления без одновременного polling двумя экземплярами.

### 4. Автоматические платежи

Текущая предоплата подтверждается вручную. Будущий платёжный модуль потребует отдельного
провайдера, webhook, статусов платежа и возврата, идемпотентности, срока резерва слота,
сверки суммы и правил действий при позднем webhook. До выбора провайдера реквизиты и
возвраты остаются ответственностью мастера.

### 5. Несколько сотрудников одного бизнеса

Текущая модель рассматривает один бизнес как календарь одного специалиста. Расширение
потребует сущности сотрудника, отдельного расписания и набора услуг, выбора исполнителя,
ролей доступа, общего ресурса кабинета и правил конфликтов между сотрудниками.

### 6. Связывание ручной клиентской карточки с Telegram

Для клиента, добавленного мастером без Telegram, перенос согласуется вне бота. Будущий
сценарий должен безопасно связать карточку после первого входа пользователя, не создавая
дубликат и не раскрывая чужие записи. Понадобятся одноразовое приглашение, срок действия,
проверка владельца и журнал объединения.

### 7. Функции вне текущего MVP

Отдельными продуктовыми этапами остаются:

- платная SaaS-подписка;
- отзывы и рейтинг;
- жалобы и модерация;
- лист ожидания;
- абонементы и пакеты занятий;
- CRM-аналитика и выгрузки;
- несколько городов и пользовательский выбор часового пояса;
- перенос интерфейса в MAX или другие каналы.

Эти функции не должны добавляться в текущие ветки календаря, базы данных или публичного
ID без отдельной постановки и изменения границ MVP.

## Ограничения текущей версии

- JSON и memory рассчитаны на один процесс и локальную проверку.
- Незавершённый FSM-ввод теряется при перезапуске.
- SQL Server-каталог пока содержит заготовки и не используется при `STORAGE=json`.
- Дата в некоторых сценариях вводится текстом до объединения задания календаря.
- Внутренний идентификатор временно используется как код до задания публичного ID.
- Резерв неизвестной длительности и ожидание предоплаты истекают через 30 минут.
- Позднюю предоплату и возвраты мастер разбирает вручную.
- Уведомление может повториться при аварии между отправкой и фиксацией результата.
- У ручной карточки без Telegram уведомление получает только мастер.
- Внутренний часовой пояс пока задаётся общей константой `Asia/Yekaterinburg` в `.env`.
